# Curating the catalog

*How to add, check and publish streams. The rules are DESIGN §7; the tool is `catalog-tool` (PLAN M7).*

## Layout

```
catalog/
  release.json        {"schema": 1, "revision": N, "generatedAt": "…Z", "expiresAt": "…Z"}   bump per publish
  engine.json         the feed's engine section; "pin" names a yt-dlp version only
  pins.json           {"asset": "yt-dlp_macos.zip", "sha256": {"<version>": "<hex>"}}     written by build
  genres/<id>.json    {"id", "name", "order", "streams": [ … ]}   one genre and its streams
  feed.json           GENERATED by `catalog-tool build`: never edit it by hand
```

`catalog/feed.json` is what the app bundles (`Contents/Resources/feed.json`) and, once hosting exists, what is
published. `catalog-tool build` writes it byte-for-byte deterministically from the files above: genres sorted by
`order` then id, streams in genre order then file order, every stream on one line with its keys in a fixed order.
A unit test (`CatalogTests/CurationTests.swift`) fails when `feed.json` is not exactly what the sources build.

## Adding a stream

Add one line to `catalog/genres/<id>.json` (keys may be in any order; `genres` is implied by the file):

```json
{"id": "mc:Defectedrecords/defected-radio-show-hosted-by-monki-021026", "source": "mixcloud", "ref": "Defectedrecords/defected-radio-show-hosted-by-monki-021026", "kind": "mix", "title": "Defected Radio Show 02.10.26", "creator": "Monki", "durationSec": 7200, "weight": 1.0}
```

| Field | Rule |
|---|---|
| `source` | `youtube`, `youtube-live`, `soundcloud`, `mixcloud`, `radio` |
| `ref` | canonical ref (DESIGN §7.1): YouTube 11-char video ID; `/live` `@handle` or `UC…` channel ID; SoundCloud `user/slug` (lower case); Mixcloud `User/slug`; radio the direct stream URL (https preferred; no IP literal, `.local`, playlist files, ports other than 80/443/1024–65535) |
| `id` | derived from the ref (`yt:`, `ytl:`, `sc:`, `mc:` + ref) and may be omitted; radio needs `radio:<slug>` |
| `title`, `creator` | the set/station and the DJ/broadcaster (the marquee reads `[GENRE] CREATOR - TITLE`); ≤ 200 characters |
| `kind` | `mix` (default), `live` (`youtube-live`), `station` (radio) |
| `durationSec` | mixes: the length in seconds (mixes should be ≥ 40 min; the catalog convention is ≥ 50) |
| `weight` | pick weight in (0, 100]: mixes 1.0, 24/7 `/live` 0.75, radio 0.5 |
| `homepage` | required for radio (credits the broadcaster) |
| `genres` | only to put one stream in several genres: list them all, this file's genre included |

A new genre is a new file `genres/<id>.json` (`id`: lower-case words joined by hyphens, ≤ 32 characters; renaming an
id later orphans favourites and history). Every genre must meet the 1.0 rule: **≥ 15 active streams, ≥ 2 radio
stations from ≥ 2 broadcasters (by `creator`), ≥ 2 source types** (YouTube VOD and `/live` count as one).

Source rules (DESIGN §7.3): SoundCloud items need policy ALLOW or MONETIZE, |duration − full_duration| < 2 s and an AAC
transcoding; Mixcloud items must not be exclusive and must probe without a `restrictedReason`; no SomaFM station
without SomaFM's permission; official label, artist, radio and festival accounts preferred.

## Checking

```sh
swift run catalog-tool lint catalog/            # every rule; exit 1 on errors (--strict: also on warnings)
swift run catalog-tool lint catalog/ --dns      # also: every radio host resolves to public addresses only
swift run catalog-tool build                    # writes catalog/feed.json (refuses on lint errors)
swift run catalog-tool build --check            # CI: exit 1 if feed.json is stale
```

`lint` rules: `json` (strict JSON, no duplicate keys), `schema` (unknown keys such as a `durationSecs` typo, types,
envelope), `canonical` (refs and IDs in canonical form), `duplicate` (genre, stream ID or radio URL twice), `radioURL`,
`coverage` (the 1.0 rule), `engine` (DESIGN §7.2's strict engine strings; a pin without a checksum), `canary` (one
YouTube VOD and one SoundCloud item, both in the catalog), `expiry` (missing, past, before `generatedAt`; a warning
within 60 days), `policy` (SomaFM; plain-HTTP radio and short mixes are warnings), `stale` (`feed.json` ≠ build).

**Probing** resolves items with a real engine through the Resolver (the app's argv, tier and media-host allowlist)
and range-GETs the result; radio is fetched and its first 32 KB checked for chained MP3/AAC/Ogg frames:

```sh
P=~/Library/Caches/sudamp-dev/probe-profile     # any directory; never the app's real profile
swift run catalog-tool probe catalog/ --profile "$P" --install-engine --source radio,soundcloud,mixcloud --json
swift run catalog-tool probe catalog/ --profile "$P" --source youtube,youtube-live --youtube-limit 5 --json
```

YouTube is rationed: at most `--youtube-limit` yt-dlp runs (default 5), ≥ 8 s apart (never less than 5), and a
bot-check, `LOGIN_REQUIRED` or 429 stops all YouTube requests for the run. Spread a full YouTube probe over days.
PLAN M7 asks for ≥ 95% passing before a release (`--min-pass 0.95` is the exit-code threshold).

**Finding candidates** (printed as JSON for a human to review; nothing is written):

```sh
swift run catalog-tool discover --genre "deep house" --limit 10 --profile "$P"
```

It queries radio-browser.info by tag (and verifies each stream), SoundCloud `scsearch` through the engine and Mixcloud's
`api.mixcloud.com/discover/<tag>/popular/`, skipping what the catalog already has. Candidates still need the source
rules above and a real `creator` for radio (it defaults to the station name).

## The engine section

`engine.json` holds DESIGN §7.1's engine fields. `pin` is `{"version": "YYYY.MM.DD"}`: `catalog-tool build` fills its
SHA-256 from upstream's `SHA2-256SUMS` (the `yt-dlp_macos.zip` line) the first time a version is pinned and records it
in `pins.json`, so later builds are offline and reproducible. `block` lists versions that must never be installed
(also honoured for updates). Every string is checked against DESIGN §7.2's rules; the app keeps the previous value of
any field that fails, `lint` makes it an error.

## Publishing (once the feed host exists)

The app fetches `<feed URL>` and `<feed URL>.sig` (GitHub Pages; the URL goes into `FeedEndpoint.production`). Release
builds with no production key, or no URL, never fetch and play their bundled snapshot.

```sh
swift run catalog-tool bump                      # revision + 1, generatedAt now, expiresAt now + 182 days
swift run catalog-tool build && swift run catalog-tool lint catalog/
swift run catalog-tool sign --key <production.key>          # → catalog/feed.json.sig (64 raw bytes)
swift run catalog-tool verify --production                  # with a build that embeds the production key
# copy catalog/feed.json and catalog/feed.json.sig to the Pages site, together
```

Rules the app enforces (DESIGN §7.2): the signature must verify against an embedded key; `revision` must be ≥ the
copy the app has cached (never publish a lower revision); `expiresAt` must be in the future (an expired document is
ignored: the app falls back to its cached copy, then the bundled one); `engine.minAppVersion` above the app's version
makes the app ignore the document. The highest valid revision among bundled, cached and fetched wins. Give each
document about six months of `expiresAt` and re-publish (bump, build, sign) before it runs out.

## Keys and signatures

- `feed.json.sig` is the **64-byte raw Ed25519 signature** over the exact bytes of `feed.json` (CryptoKit,
  `Curve25519.Signing`). Readers also accept the same 64 bytes as one line of standard base64. Signatures are
  randomised: signing twice gives different, equally valid files.
- Private key file: one line `ed25519-private:<base64 of the 32-byte raw key>`, mode 0600. Public key file: one line
  `ed25519-public:<base64 of the 32-byte raw key>`; the bare base64 is the form embedded in the app.
- `swift run catalog-tool keygen --out ~/sudamp-feed-2026` writes both files (never overwriting) and prints the line to
  add to `FeedTrust.productionKeys` (`Sources/Feeds/FeedTrust.swift`). The app embeds **two** keys for rotation:
  ship a release with the current and the next key, start signing with the next key, then drop the old one.
- Where the production private key lives is the owner's choice: an offline file, or the login Keychain, e.g.
  `security add-generic-password -a sudamp -s sudamp-feed-key -w "$(cat ~/sudamp-feed-2026.key)"` and later
  `security find-generic-password -a sudamp -s sudamp-feed-key -w | swift run catalog-tool sign --key -`
  (`--key -` reads the key line from stdin; the Keychain route is documented, not tested here).
- `Fixtures/keys/test-ed25519.{key,pub}` is a **test** keypair with a committed private half. Only debug builds trust
  it; never sign anything published with it.

## Testing against a local feed (debug builds)

```sh
python3 -I Fixtures/feeds/serve.py Fixtures/feeds/block-latest --port 18471 --log /tmp/requests.jsonl &
P=$(mktemp -d)
SUDAMP_FEED_URL=http://127.0.0.1:18471/feed.json swift run catalog-tool fetch --profile "$P" --choose
SUDAMP_FEED_URL=http://127.0.0.1:18471/feed.json swift run catalog-tool fetch --profile "$P" --choose   # now 304
```

`fetch` runs the app's launch sequence headlessly (bundled feed, `<profile>/feed/` cache, refresh with a 5 s budget,
then EngineStore's version choice) and records `feed.fetched`, `feed.status`, `feed.rejected` and `engine.choose` in
`<profile>/Logs/metrics.jsonl`. `serve.py --blackhole --port 18472` is a host that never answers.
