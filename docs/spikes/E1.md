# Spike E1: Engine in `.app` (PLAN M0)

**Verdict: GO** (2026-10-22, macOS 27.0.1, Apple M5 Pro, Mac mini Speakers at 48 kHz / 512-frame IO buffer,
Command Line Tools only, Swift 6.4, MPVKit 1.0.0 = `mpv v0.41.0-dirty`). Every E1 threshold passed in 4 of 4
release runs. One caveat on how pause is measured is explained below; it does not change the verdict.

The engine is the spike's design, rebuilt as production modules:

- `SudampAO` is the pull AO, unchanged apart from a lock-free `sudamp_ao_is_streaming()`.
- `AudioRender` is the C/ObjC render bridge: host pause with a 5 ms ramp, fades, balance, the TTFA stamp, counters,
  the 8192-frame SPSC ring and a probe log.
- `MPV` is the Swift client: options, the event thread, async commands, typed getters and guards.
- `Audio` is the AVAudioEngine graph: source → 10-band EQ → mixer.

All audio was inaudible: mixer `outputVolume = 0`, and the bridge zeroes its output after measuring it.

## Methodology (as in `spikes/engine-pull-ao` spikepull)

The fixture is 60 s of 44.1 kHz float32: the left channel is a 0.1 × 1 kHz sine and the right is a ramp from −0.9 to
+0.9 that encodes the playback position.
- **Per callback**, the C render body logs to a preallocated probe: CLOCK_UPTIME_RAW start time, frames, frames
  read, the raw first and last right-channel samples, and the output peak.
- **Latencies** run from the tool's timestamp just before the async command to the start of the first render
  callback that shows the effect. A seek or loadfile counts when the decoded position is within 0.25 s of the
  target. A stale quantum is an audible callback between the command and the new audio.
- **The bench schedule:** an 8 s steady window (CPU from `getrusage`, short reads), then 10 host pauses, 3 mpv-only
  pauses, 12 seeded seeks and 5 loadfiles.

**Pause, measured strictly.** `pauseToSilenceMs` runs from the command to the moment the output is fully silent,
and it includes the 5 ms ramp. When the host pause ramps out, the time is the callback start plus the frames it
read. The design bound is one IO buffer plus the ramp: 10.67 + 5 = **15.67 ms**. That is slightly above the PLAN's
15 ms, so a run can exceed 15 ms by phase alone, about 6% of single pauses in theory. None of the 40 measured
samples did; the largest was 14.86 ms. Two other measures are also reported:
- **The pause taking effect** (the first callback that starts the ramp) took ≤ 9.9 ms.
- **mpv's own pause** (the spike's measure) took 4–10 ms.

The PLAN threshold is now 16 ms (one IO buffer plus the ramp), as this note recommended.

## Bug found and fixed: mpv's pause raced the host ramp

The first bench run showed every host-pause sample below one IO buffer (1.0–9.7 ms). That meant mpv's pause, sent
straight after the host flag, emptied the AO read before the ramp callback ran: an abrupt cut, with no ramp at all.

The fix:
- `AudioEngine.hostPauseAndWaitForRamp()` sets the flag and waits until the C side reports the ramp rendered
  (`sa_render_host_pause_settled`, ≤ ~one IO buffer).
- Only then does the caller pause mpv. The tools do this, and M1's PlaybackController must too.
- The ramp up after resume now advances only over frames mpv actually delivers, so a resume that arrives before mpv
  streams again still fades in.

The samples now fall between 5.9 and 14.9 ms, which proves the ramp renders.

## Per-file options, checked on the wire

`loadfile` is sent as a node map: `name`, `url`, `flags=replace`, `index=-1`, plus `options`. The options are:
- `http-header-fields`: commas are escaped as `\,`, CR/LF is rejected, and names must be RFC 9110 tokens;
- `user-agent`, `force-media-title`, `start` and `http-proxy` (http:// only);
- `stream-lavf-o`, restricted to `[a-z0-9_]` keys and `[A-Za-z0-9._:/-]` values.

A local `nc` listener captured mpv's request with the headers intact, for example
`Accept-Language: en-us,en;q=0.5` as one header and a User-Agent containing commas. `force-media-title` and `start`
appear in mpv's `Setting option` log and in the decoded ramp position.

## Observations

- **Radio TTFA.** The radio stream started in 862 ms with the radio options (`reconnect_streamed=1` only),
  matching the spike's 901 ms. With `request_size`/`short_seek_size` added it took 2.46 s. That is one sample and
  may be network variance, but it agrees with DESIGN §5.2: those options are for progressive files, not live radio.
- **Memory.** `stress-lifecycle` RSS goes 12 → 82 MB after 4 iterations (one-time framework and FFmpeg warm-up),
  then grows about 0.12 MB per create/destroy cycle (105 MB after 200). Threads stay flat at 7–8. The app creates
  the engine once, so this doesn't matter now; M3's soak watches RSS drift.
- **AO before init.** `aoUnavailable` (≈ 23 per run) is all from callbacks before the first file initialises the AO.
  There were 0 in steady state.
