# Spike E2: Device change (PLAN M0)

**Verdict: GO, via the PLAN's fallback (`kAudioOutputUnitProperty_CurrentDevice`).** Run on 2026-10-22: macOS
27.0.1, Mac mini Speakers, release `sudamp-dev`. The (manual) 5-cycle Bluetooth headphone checklist was **not run**:
it needs a human with headphones.

## Command

```
/tmp/…/run.sh --cycles 20 --json      # wraps: trap 'sudamp-dev devswitch --restore' EXIT; sudamp-dev devswitch "$@"
```

- **The aggregate.** `devswitch` creates a non-private aggregate device, "sudamp devswitch (temporary)",
  UID `app.sudamp.devswitch.<pid>`, wrapping the built-in output.
- **The toggles.** The ramp fixture loops silently (mixer volume 0, bridge output muted) while the tool toggles
  `kAudioHardwarePropertyDefaultOutputDevice` between the aggregate and Mac mini Speakers, holding each for 2 s.
- **Exit traps.** The original default output, the system output and the aggregate are restored or destroyed from
  `atexit`, from SIGINT/SIGTERM/SIGHUP DispatchSources, best-effort from crash signals, and from a state file that
  `devswitch --restore` replays after a SIGKILL.
- **Restore result.** Every run ended with `restoredOriginalDefault: true`, the aggregate destroyed, and
  `system_profiler` showing Mac mini Speakers as the default output again.

## Step 1: do default-device toggles produce `AVAudioEngineConfigurationChange`? No.

| Observation (12 toggles in 4 runs: one observe-only run of 6, plus the 2-toggle detection step of 3 runs; 3–3.5 s window each) | Result |
|---|---|
| `AVAudioEngineConfigurationChange` after a default-output toggle | **never** |
| Engine output device after the toggle | stays on Mac mini Speakers (no move to the aggregate) |
| Render callbacks across the toggle | uninterrupted (max gap 10.7 ms): the engine just keeps playing on the old device |

On macOS 27 AVAudioEngine does not follow, or report, a change of the default output to this same-format device
(48 kHz, 2 ch). So, per the PLAN, the tool switches the device itself. M3 needs a real mechanism for this anyway,
so it is built into `AudioEngine`, not just the tool.
- **The listener.** `setFollowsDefaultOutput(true)` installs a HAL listener on
  `kAudioHardwarePropertyDefaultOutputDevice`.
- **The recovery path.** The listener drives the same debounced recovery as configuration changes: on the first
  trigger, host pause and pause mpv; after a 150 ms quiet window, `stop()`, then bind
  `kAudioOutputUnitProperty_CurrentDevice` on `outputNode.audioUnit`, then `reset()`, reconnect, `start()` (3
  tries, then rebuild), then resume mpv and the host with a 50 ms fade.
- **Soft recovery.** If the engine is already running on the wanted device when the window closes, nothing is
  restarted. Our own device switches can post a late, self-inflicted notification.

Per-switch pattern, identical in both runs:
- **To the aggregate.** The listener fires; after the 150 ms debounce the engine is moved (`moveDevice`) and
  restarted. The render gap is about 65–75 ms and audio returns at 205–230 ms.
- **Back to the built-in.** The output unit had already followed by itself (render gap about 75 ms). The recovery
  finds the engine healthy (`none`), and audio is back at about 155–170 ms. That is the host pause lasting through
  the debounce.
- **The first move only (cycle 0).** Binding the fresh aggregate posts one self-inflicted
  `AVAudioEngineConfigurationChange` about 320 ms after the toggle. The engine has stopped itself, so a second
  recovery restarts it, and audio returns at **493–495 ms**. That is inside the limit, but by less than 10 ms.

## Follow-ups for M3 (not blocking E2)

The first two are fixed in M3; see "M3 follow-up" below and `docs/spikes/M3-audio.md`.

- **The first-move margin is thin.** A configuration change arriving within about 1 s of a device move we made
  ourselves could use a much shorter debounce, or the move could rebuild the engine with the device bound before its
  first start. Re-measure on Bluetooth: that is the manual checklist.
- **Back-to-built-in pays about 150 ms of silence** only because we host-pause before knowing the engine already
  followed. Check `outputDevice` before pausing.
- **Following the default output must be on in the app.** Without the listener, a user who picks another output in
  Control Center keeps hearing sudamp on the old device.
- **The recovery report says what happened.** `RecoveryReport.action` (`none` / `restart` / `moveDevice`) and
  `ConfigurationStats.defaultOutputChanges` are already exposed for M3's state.json.

## M3 follow-up (2026-10-22): first move and return to the built-in output

Two changes to `AudioEngine`'s recovery (M3, audio agent):

- **A move binds the device before the first start of a fresh engine.** Instead of rebinding the running engine's
  output unit, the recovery builds a new AVAudioEngine, sets `kAudioOutputUnitProperty_CurrentDevice`, then attaches,
  connects and starts it. The self-inflicted `AVAudioEngineConfigurationChange` on the first move is gone (0 in 200
  switches). A configuration change within 1.5 s of our own start also gets a 10 ms quiet window instead of 150 ms,
  and a trigger that lands during a recovery schedules a re-check. With that short window alone (the first variant
  tried) the first move took 375.6 ms.
- **Nothing pauses until a restart is needed.** The recovery checks the device after the quiet window: if the output
  unit already followed the default (the return to the built-in), audio keeps playing; otherwise it host-pauses
  (waiting for the ramp), pauses mpv, moves, and resumes with the 50 ms fade.

`devswitch` now measures more strictly: a watcher thread records when the output unit first reports the target
device, and audio counts from the first audible callback after the last gap of ≥ 25 ms on that device (so a later
dropout, or audio still on the old device, can't flatter a switch). The M3 baseline below is the pre-change engine
under that metric.

The first move now has about 250 ms of margin. Moves to the aggregate are about 17 ms slower (the ramp wait and the
rebuild), but audio keeps playing on the old device during the quiet window, so silence per switch fell to ~77 ms.
The (manual) Bluetooth checklist is still not run.
