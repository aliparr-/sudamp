## Soak

`sudamp-dev soak` supervises `sudamp-dev play` in a child process and samples its memory every 30 s; RSS is
`ri_resident_size`, footprint `ri_phys_footprint` (`proc_pid_rusage`); drift = last sample − first sample after the
warm-up (10 % of the run, ≤ 5 min). Sources: SoundCloud, Mixcloud and radio — **YouTube excluded** to keep the
YouTube budget (a 2 h soak with YouTube would spend ~25 resolves); YouTube playback, refresh and recovery are covered
by the gate runs above. Binary: the final code except the 10 s playing debounce and `engine status` output (no path
loss happened during the soaks).

| Soak | Duration | Crashes | Starts (success) | RSS (drift) | Footprint (drift) | TTFA |
|---|---|---|---|---|---|---|
| `--minutes 35 --skip-every 1m` | 2100.6 s, 1 child | **0** | 35 of 35 (**100 %**): 16 Mixcloud, 10 radio, 9 SoundCloud; 34 prefetched | 219.6 → 238.3 MB (**+18.7**) | −10.4 MB (ends at 27.4 MB) | p50 1308 ms, p90 1935 ms |
| `--hours 2 --skip-every 10m` (PLAN shape) | 7199.6 s, 1 child | **0** | 12 of 12 (**100 %**): 5 Mixcloud, 4 SoundCloud, 3 radio; 11 prefetched | 220.2 → 243.1 MB (**+22.9: misses < 20**; peak 257.9 at 5700 s) | **−33.4 MB** (60.4 → 27.0 MB) | p50 1514 ms, p90 3563 ms (the first, cold pick 8882 ms) |

The 35-minute soak passes every PLAN threshold. The 2-hour soak has 0 crashes and 100 % starts but **misses the RSS
criterion by 2.9 MB**, so the soak gate is **PARTIAL**. What the data says: RSS steps up by 2–22 MB at some new mixes
(+9.4 MB at the first Mixcloud mix, +5 MB at 4500 s, +21.7 MB at 5700 s, two thirds of it released by the end) while the
physical footprint — the dirty memory macOS charges the process — ends 33 MB *below* its baseline and stays at
27–30 MB between picks. That reads as freed pages the allocator keeps resident, not a leak; but it is not proven.
Isolated checks didn't reproduce the creep: 30 loads of one radio station (pre-M6 binary 198.8 → 198.8 MB, this one
199.1 → 201.1 MB, footprint 36.5 MB in both) and 8 loads of one Mixcloud mix (a 212–222 MB sawtooth, no trend, with or
without a `malloc_zone_pressure_relief` call after each start — so that change was not kept). Next step (open
issue): a `heap`/`leaks` session on a long mixed soak. An earlier 2 h attempt with the pre-fix cache settings was
stopped at 24 min: RSS 457 MB, footprint 262 MB, ~+115 MB at each new mix (see Findings).

## Security item: radio redirects

FFmpeg followed station redirects itself, so only the first host passed the private-address rule. Mitigation built:
FFmpeg now follows **no** redirect (`stream-lavf-o` `max_redirects=0`, an option this FFmpeg n8.1.2 build has); the
controller follows them with URLSession, **one hop at a time**, each target re-checked with `RadioURLPolicy` and
`RadioHostCheck` (IP literals, `localhost`, `.local`, private/link-local/loopback answers refused), and remembers each
station's hop count in `session.json` (`radioRedirectHops`). A station with a known count is walked exactly that many
hops (our requests replace FFmpeg's own one for one) and FFmpeg opens the last checked URL, which is never fetched
twice. A first play goes straight to FFmpeg; if it fails, one more hop is asked for, checked, and opened in the same
attempt (up to 3 times, 5 hops in all); no redirect means a genuine failure. A refused hop fails the station as
`unavailable`.

Cost, `ttfa --source radio` (n = 8 per run, cold picks across the 17 curated stations, 7 of which redirect):

| | p50 | mean |
|---|---|---|
| FFmpeg following redirects (`--radio-redirects=false`), 3 runs, n = 24 | 708 ms | 893 ms |
| First design (walk every hop *including* the final one before FFmpeg opens it), n = 16 | 1172 ms | 1317 ms |
| Built design, runs 1–3 in one profile (hop counts being learnt) | 1205 / 1432 / **652** ms | 1251 / 1245 / **916** ms |

So the steady state costs nothing measurable (run 3: p50 652 vs 643–843 ms without); the first play of a redirecting
station pays about one failed FFmpeg attempt per hop (~0.3–0.6 s), once per profile. Residual risks, documented:
DNS rebinding between our lookup and FFmpeg's; hosts of HLS radio segments; redirects only FFmpeg parses (an
`ICY 302` status line) now fail to open rather than being followed; plain-HTTP stations can't be walked by URLSession
under ATS (all curated stations are HTTPS; a pasted `http://` station that redirects fails to open).

## Optional performance item: HLS opens (time-boxed, not adopted)

The double fetch M1 saw is mpv's **refresh seek**: `demux_lavf` reads `init.mp4`, `data000`, `data001` while opening
(FFmpeg's HLS header + `avformat_find_stream_info`), then mpv selects the audio track, which issues `refresh seek to
0.000000`, and FFmpeg's HLS demuxer re-opens `init.mp4`, `data000`, `data001`. mpv -v timeline of a saved SoundCloud
resolution (scratch harness, not committed): playlist 0 ms → `hls` found 199 → opening done 613 → refresh seek 614 →
AO 824 → first audio 894 ms; the second round costs ~210 ms. Tried per file and globally:
`demuxer-lavf-probe-info=no`, `demuxer-lavf-analyzeduration=0.1` — the refresh seek happens in every case (it depends on
the stream being seekable and selected after open, which no option changes short of `cache=no`/unseekable), and
`ttfa --source soundcloud -n 6` HLS-open (TTFA − resolve) p50 was 963 ms baseline vs 1003 ms with `probe-info=no`
(noise). Not adopted. A debug-only knob stays for future A/B runs: `SUDAMP_HLS_OPTS` / `SUDAMP_LOAD_OPTS`
(`name=value;…` per-file mpv options).

## Findings

- **mpv's demuxer cache grew without bound per stream (fixed).** The first 2 h soak attempt (a build before this fix) reached
  RSS 457 MB / footprint 262 MB after 24 min, jumping ~115 MB at each new mix. Two causes, both measured on a pinned
  one-station feed: (1) with `cache=yes`, mpv's `cache-secs` (default: practically unlimited) overrides
  `demuxer-readahead-secs=30`, so a VOD is read ahead to `demuxer-max-bytes` (64 MiB) — a whole Mixcloud mix,
  ~110 MB of footprint within 15 s of the pick; (2) played packets stay in the back buffer up to 50 MiB *plus* the
  forward cache's unused share (`demuxer-donate-buffer=yes`), ~1.1 MB per 20 s on a 1.FM station (the pre-M6 binary
  does the same: 0.95 MB / 20 s on Technolovers). With `cache-secs=30`, `demuxer-donate-buffer=no` and `demuxer-max-back-bytes`
  8 MiB / 1 MiB per file: radio footprint flat over 160 s (28.3 → 28.5 MB; before: +1.1 MB / 20 s); a Mixcloud VOD
  starts 110 MB lower and plateaus once its 8 MiB back buffer is full (~160 s). `demuxer-max-back-bytes` alone does
  nothing while donation is on.
- **A cold engine copy resolves slowly.** The first YouTube resolve in a profile whose engine was just copied took
  6.6 s (1.5 s warm), the first SoundCloud picks 3–4 s: none of its 128 MB is in the page cache. The launch warm-up
  helps only when it isn't pre-empted (it is, by an immediate user pick — by design, it never delays one).
- **The canary competes for YouTube tokens.** Under `youtube:403`, failing picks spend 2 tokens each (tier 1 + tier 2),
  so the failure-triggered canary waited ~30 s per YouTube check for a token. That is DESIGN §6.3's shared bucket
  working as intended; the check runs in the background.
- **Swift Testing's `#expect` re-evaluates mutating calls** in a failing expectation and misreads `x == 6 * 3600`
  against a `Double?` (the integer literal product); the tests bind results first and use `TimeInterval(…)`.
- **Async overloads win over actor methods.** A protocol-extension `async` default beat `StreamResolver`'s own
  synchronous actor method in an `await` call (and is all an existential sees unless declared in the protocol): the new
  `StreamResolving` hooks are protocol requirements with defaults.
