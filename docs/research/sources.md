# Stream sources (yt-dlp: YouTube, SoundCloud, Mixcloud, radio)

## SUMMARY
yt-dlp is still the practical engine for all three sites. I checked docs and source, and also ran the official yt-dlp 2026.10.21 macOS build from a residential UK IP on 2026-10-22. Without any JavaScript runtime, YouTube played audio-only itag 251 (opus) and 140 (m4a) through the JS-less `visionos` client in 1.2–1.4 s. Live 24/7 streams return HLS audio-only itags 233/234 with no PO token. SoundCloud resolves in about 0.6 s and is HLS AAC only now (160k/96k). Mixcloud resolves in about 1.0 s (HLS AAC 64/192k, progressive m4a, DASH opus). Three new problems: (1) with a JS runtime enabled, the default `tv_samsung` client's format URLs carry a forced ~5 s "pre-roll ad" wait (`available_at`) and return HTTP 403 until it passes. (2) The Deno team announced on 2026-10-09 that it will stop developing the Deno runtime after one more year, and Deno is yt-dlp's default runtime. (3) Breakage is real: a 7-month-old yt-dlp (2026.03.17) still "resolved" URLs today but they returned 403, while the 2-month-old 2026.08.19 worked. So a controlled engine-update channel is mandatory, not optional.

For packaging, ship the onedir build (`yt-dlp_macos.zip`, universal, 123 MB unpacked, about 0.15 s warm start) rather than the onefile `yt-dlp_macos` (37 MB, about 1.5 s start on every call, and its embedded dylibs can't be re-signed for notarization). For the JS runtime, the choice is between no runtime (works today, but yt-dlp calls it deprecated), QuickJS-NG (1.3 MB, but about 3.5 s per resolve), Deno (81 MB arm64 only, end-of-life about Oct 2027) or the 27 KB `yt-dlp-apple-webkit-jsi` plugin, which uses the system WebKit and worked here in 1.6–2.1 s. The app has to be Developer ID-signed and notarized and distributed outside the Mac App Store (App Store guidelines 2.5.2 and 5.2.3 rule it out). Engine updates should be downloaded into Application Support, never into the .app bundle. Pre-resolving the next random pick hides nearly all latency, but YouTube URLs expire after about 6 h and are tied to the user's IP (`ip=` parameter).

On terms of service: YouTube's ToS and API Developer Policies explicitly forbid unauthorized access and download, automated access, circumventing protections, separating audio from video, and background players. The official SoundCloud API terms forbid apps that mix SoundCloud with other services (their example is "SoundCloud with YouTube") and webcasting radio apps, so the official API is no compliant way out for sudamp's concept. Mixcloud says audio streams are only available through its widget, which must be visible on screen. Open-source extraction clients (NewPipe, FreeTube, yt-dlp itself, Metrolist) have not been sued away. The 2020 RIAA takedown of youtube-dl was reversed, but a German appeals court in 2024 held YouTube's "rolling cipher" to be an effective technical protection measure. In practice the risks are breakage, IP or bot-check blocks for users, and pressure on distribution, not lawsuits against users. Internet radio (radio-browser.info) needs no extraction, starts instantly, and is the right 4th source type and fallback. (My test scripts and downloads are in /tmp/sudamp-research; nothing in the repo was touched.)

## RECOMMENDATION
**Architecture.** Add a `StreamResolver` protocol with one strategy per source (youtube, soundcloud, mixcloud, radio). Use libmpv for playback with `ytdl=no`. Swift resolves every URL itself and passes direct media URLs plus headers to mpv.

**1. Engine**
- Bundle the yt-dlp onedir build (`yt-dlp_macos.zip`, a stable or nightly tag that passed your smoke tests). Re-sign every Mach-O with your Developer ID and hardened runtime (test whether curl_cffi/ctypes needs allow-unsigned-executable-memory), notarize the app, and distribute via DMG, Sparkle and a Homebrew cask. Not the Mac App Store.
- Optionally thin to arm64 to save about 60 MB.
- Bundle QuickJS-NG `qjs` (1.3 MB per arch) and the `yt-dlp-apple-webkit-jsi` plugin zip (27 KB) under `Contents/Resources/engine/plugins`. Don't bundle Deno (81 MB per arch, end of development about Oct 2027).

**2. Invocation (one process per resolve)**
- Base command: `yt-dlp --no-config --ignore-config --cache-dir ~/Library/Caches/sudamp/yt-dlp --no-playlist -q --no-warnings --plugin-dirs <bundle>/plugins --js-runtimes quickjs:<bundle>/qjs -J <url>`.
- YouTube VOD: add `--extractor-args "youtube:player_client=visionos,tv_samsung" -f "bestaudio[ext=webm][format_id!*=drc]/bestaudio[format_id!*=drc]/bestaudio"`.
- YouTube live (catalog stores channel `/live` URLs): `-f "bestaudio[protocol^=m3u8]/best[protocol^=m3u8]"`.
- SoundCloud: `-f "hls_aac_160k/hls_aac_96k/bestaudio"`.
- Mixcloud, if included: `-f "hls-192/http/bestaudio"`.
- From the JSON, take `url`, `http_headers`, `available_at`, `duration`, `live_status` and the `expire`/`expires` query parameter.
- Keep the client list and format strings in remote config, not code.

**3. Playback settings (mpv)**
- Wait until `available_at` has passed.
- Set `http-header-fields` from the JSON, `stream-lavf-o=request_size=10485760` (or `curl-max-request-size` on newer mpv), `network-timeout=10` and `cache=yes`.
- On load failure or 403: re-resolve once, then move on to the next pick within about 1 s.
- For live and very long mixes: re-resolve when mpv reports an error or end of file, and proactively before expiry.

**4. Latency**
- Keep 1–2 pre-resolved picks per active genre (also lets the 5 s pre-roll wait pass) and check each with a 64 KB range GET.
- Cache them until expire − 15 min. Drop cached YouTube URLs when the network path changes (they're IP-bound).
- Target time-to-first-audio is under 1 s with a pre-resolved pick. A cold YouTube pick takes about 1.5–2.5 s; SoundCloud about 1 s.

**5. Engine updates**
- Never use `yt-dlp -U`. A CI job (macOS runner) polls yt-dlp stable and nightly, runs smoke tests (YouTube VOD and live, SoundCloud, Mixcloud resolve plus fetch), re-signs and notarizes the onedir zip, and publishes a manifest signed with Ed25519 (Sparkle-style).
- The app checks daily, and immediately after 2 consecutive YouTube failures. It verifies the signature, unpacks to `~/Library/Application Support/sudamp/engines/yt-dlp/<ver>/`, switches atomically and keeps the previous engine for rollback.
- Stay non-sandboxed and don't set LSFileQuarantineEnabled. Notarize engine builds anyway.

**6. Sources for v1**
- Include YouTube (VOD mixes plus 24/7 `/live`), SoundCloud and Radio (radio-browser plus a few hand-picked stations).
- Make Radio the automatic fallback when YouTube resolves fail or hit bot checks.
- Mixcloud: either defer it, or ship it as a 'widget mode' (a small visible WKWebView player docked as a Winamp-style mini panel) to follow Mixcloud's rules. Use the Mixcloud API for discovery either way.

**7. Curation (server-side, offline batch)**
- Discover via flat listings (`ytsearchN:`, channel `/videos` and `/streams`, `scsearchN:`, SoundCloud users and sets) and the Mixcloud API (`/discover/<tag>/popular/`, `/tag/<tag>/?metadata=1`).
- Filter: duration ≥ 30–40 min (or live), not `is_upcoming`, availability public, age_limit < 18.
- SoundCloud accept rule: policy ALLOW or MONETIZE, duration ≈ full_duration, a non-encrypted, non-snipped AAC transcoding exists.
- Validate each item with a real resolve plus range fetch, re-validate weekly, and accept anonymous 'dead item' reports from clients.
- Run YouTube validation from a residential connection or at a low rate; datacenter IPs get bot-checked much more (from memory/community reports).

**8. Don'ts**
- No cookies by default. No PO-token plugins. No `player_skip=webpage`. No offline downloads or caching to disk. Credit and link uploaders and sources in the UI.

## RISKS
- [high] YouTube changes (client deprecation, PO-token enforcement on token-free clients, SABR-only for all clients, longer ad-waits) break playback for days to weeks -> Own the engine update channel (ship within 24 h of a fix in yt-dlp nightly), keep client and format config remote, fall back automatically to SoundCloud or Radio, and run nightly CI smoke tests that alert you before users notice.
- [high] An old bundled engine returns URLs that 403 (seen with the 7-month-old 2026.03.17 today), so users on stale installs get silent failures -> Check every URL with a range GET before playback, check for engine updates on first failure, and show a clear 'updating stream engine' state instead of skipping silently.
- [medium] Per-user bot checks or 429s ('Sign in to confirm you're not a bot'), which reportedly lasted up to 2–3 weeks for one user -> Keep request volume low (shallow pre-resolve, caching), back off exponentially, switch the genre's source mix to SoundCloud and Radio while blocked, and never use the user's Google account by default.
- [medium] Takedown or DMCA §1201 / EU anti-circumvention action against sudamp's repo or download host (OLG Hamburg treats YouTube's cipher as an effective TPM), or Apple revoking the Developer ID -> Keep circumvention logic in upstream yt-dlp (downloaded engine) rather than sudamp source, avoid app stores, avoid 'download' features and wording, mirror releases, and get legal advice on EU distribution.
- [medium] Deno end of development (about Oct 2027) or breakage of the private EJS plugin hook used by apple-webkit-jsi -> Ship QuickJS-NG as the guaranteed runtime, track yt-dlp PR #15041 (JavaScriptCore), and make the runtime selection remote-configurable.
- [medium] Gatekeeper or notarization problems with the PyInstaller engine (re-signing onefile is impossible; quarantined ad-hoc updates get blocked; hardened runtime may break ctypes/curl_cffi) -> Use onedir, re-sign all Mach-Os in CI, notarize engine zips, keep the app non-sandboxed without LSFileQuarantineEnabled, verify downloads with your own signature, and test on a clean macOS VM each release.
- [medium] Hard terms-of-service conflicts: SoundCloud API terms ban mixing with YouTube and radio apps; Mixcloud forbids circumventing restrictions and limits free playback; YouTube forbids audio-only and background play -> Accept that 'unofficial client' is the honest position. Credit and link creators, don't strip or skip in ways that defeat licensing (or use the Mixcloud widget), offer no downloads, and add a clear disclaimer. Be ready to drop a source if asked.
- [low] Specific CDN edges unreachable or slow (one googlevideo edge timed out in testing), plus 32 KiB/s throttling on unbounded ranges -> Short network-timeout, auto re-resolve or skip, and FFmpeg request_size=10 MiB chunking in mpv.
- [low] Catalog rot: 24/7 live video IDs rotate, region locks invisible from the curation server, Go+ snippets or DRM-only SoundCloud tracks slip in -> Store channel /live URLs, apply the SoundCloud policy/duration/transcoding rules, re-validate weekly, and collect client-side failure reports with country codes.

## OPTIONS
- A. yt-dlp onedir engine, spawned per resolve, with a sudamp-managed update channel (recommended): Recommended for v1. It's the most robust and lowest-latency setup that still relies on proven tooling.
- B. Pass page URLs straight to mpv's ytdl_hook (the IINA way): Prototype only.
- C. Embedded Python runtime with yt-dlp as a library (persistent JSON-RPC worker): Good v2 option if update size or code-signing friction with A becomes painful.
- D. Official embeds and APIs only (YouTube IFrame, SoundCloud widget or API, Mixcloud widget): Not viable as the main path. Mixcloud widget mode is a reasonable compliant option for that one source.
- E. Native Swift extractor (own InnerTube client or a Swift YouTube library): Reject.
- F. Internet radio as a 4th source and automatic fallback: Add in v1, both as a selectable genre source and as the automatic fallback when YouTube resolution fails repeatedly.

## MISSED CONSIDERATIONS
- Runtime and plugin isolation in the base command. `--no-config` and `--ignore-config` are aliases, so passing both is redundant. More important is `--no-plugin-dirs` before `--plugin-dirs <bundle>`: yt-dlp loads plugins from all default locations (~/.config/yt-dlp/plugins, ~/.yt-dlp/plugins, …), so a user's own plugins could change or break extraction inside sudamp. Also pass `--no-js-runtimes` before any `--js-runtimes` so runtime choice is deterministic (README).
- Read available_at as a timestamp, not a flag. It is set on every format (int(now) when there is no ad), and the wait is the total ad length or skip offset, which can be well over 5 s. Cold-start time-to-first-audio with tv_samsung can be 15–30 s+, not just 5 s.
- Token-free clients don't avoid bot checks. In #17406 and #17690 (Aug–Sep 2026), visionos itself returned LOGIN_REQUIRED, and maintainers asked whether users were on a VPN or VPS. Many listeners use VPNs. The only community fixes were cookies (web_embedded) or curl_cffi impersonation, so with a 'no cookies, no PO token' policy, YouTube simply goes away for blocked users. visionos also can't play 'Made for kids' videos (_base.py comment).
- SoundCloud: pass `--extractor-args "soundcloud:formats=hls_aac"`. The extractor makes one api-v2 call per transcoding (default http_aac, hls_aac, http_opus, hls_opus, http_mp3, hls_mp3), and source comments flag 429 risk. Also, the API terms ban even a SoundCloud-only genre radio ('aggregates and streams User Content from multiple users into an on-demand listening service'), not just mixing with YouTube.
- Licence obligations for the bundled engine. The official yt-dlp PyInstaller builds include mutagen (GPL-2.0-or-later), LGPL libs (libintl, libidn2, libunistring) and certifi (MPL-2.0), so redistributing them needs licence texts and source offers (THIRD_PARTY_LICENSES.txt). libmpv is GPL unless built with -Dgpl=false (brew mpv: GPL-2.0-or-later AND LGPL-2.1-or-later). IINA is GPL-3.0, so don't copy its code into a non-GPL app. QuickJS-NG is MIT, and the WebKit plugin is Apache-2.0.
- Bundle layout for notarization. Apple's 'Placing content in a bundle' says misplaced code can fail notarization. Mach-O files (qjs, the PyInstaller onedir executable and its _internal .so/.dylib/Python.framework) belong in Contents/Helpers, MacOS or Frameworks, not Contents/Resources as the recommendation proposes (only the pure-Python plugin zip is fine there). Sign inside-out without --deep.
- Platform baseline. macOS 27 runs only on Apple Silicon and is the last release with full Rosetta, and Homebrew moved Intel to Tier 3 in Sept 2026. Decide the minimum macOS: arm64-only thinning (about −60 MB) fits a macOS 27+ target, while supporting Intel Macs on macOS 26 means keeping universal builds.
- ATS covers sudamp's own URLSession calls but not mpv/FFmpeg sockets. The proposed '64 KB range GET' check on http:// radio or stream URLs would be blocked by ATS unless exceptions are configured or the check runs through mpv or curl. NSAllowsArbitraryLoadsForMedia only covers AVFoundation.
- Upstream verification in CI. yt-dlp releases ship SHA2-256SUMS.sig and SHA2-512SUMS.sig (GPG), but the built-in updater checks only hashes. sudamp's CI should verify the GPG signatures, and should honour `_update_spec` lock lines (minimum-OS pins) when choosing builds.
- libmpv source matters. No mpv release has shipped since 0.41.0 (Dec 2025). The ytdl_hook fixes (request_size, curl-max-request-size, available_at deferral) and mpv's new curl-based options exist only on master, and a lot of FFmpeg http range fixes landed 2026-10-12. Pin and test a specific libmpv/FFmpeg build (MPVKit or your own) rather than assuming brew versions.
- Mixcloud widget mode in a WKWebView needs mediaTypesRequiringUserActionForPlayback = [] for autoplay (the widget docs warn that play() may be blocked). The widget also has to stay visible, which clashes with skinning.
- Concurrency. Pre-resolving 1–2 picks per genre means parallel yt-dlp processes sharing one --cache-dir (SoundCloud client_id, YouTube player JS cache). Check for cache-write races, or serialize resolves.
- Python 3.10 EOL (yt-dlp 2026.07.04 notice) matters only for option C. The onedir build carries its own Python 3.14.

## RECOMMENDATION ASSESSMENT
The overall direction holds up. yt-dlp onedir spawned per resolve, sudamp resolving URLs itself, libmpv with ytdl=no, radio as source and fallback, and Mixcloud deferred or widget-only are all consistent with the primary sources. The version, client and policy facts were almost all accurate as of 2026-10-22. Four things should change before building on it:

1. **JS runtime selection is wired backwards.** The WebKit plugin's preference is 500, QuickJS is 850 and Deno is 1000. With the proposed `--js-runtimes quickjs:<path>` base command, QuickJS (~3.5 s) wins and WebKit is only a fallback. Use `--no-js-runtimes --no-plugin-dirs --plugin-dirs <bundle>/plugins` normally, and add `--js-runtimes quickjs:<path>` only on retry. Alternatively, accept QuickJS as primary and budget for the latency.

2. **Treat available_at as a variable wait, not a 5 s constant.** Keep the visionos-first order, but expect visionos to be bot-checked too (LOGIN_REQUIRED in #17406/#17690). The real fallback for a blocked user is SoundCloud or radio, not another client.

3. **The engine-distribution plan conflicts with the legal mitigation.** If sudamp's CI re-signs, notarizes and hosts yt-dlp, sudamp is distributing the circumvention tool, which is the exposure OLG Hamburg addressed. Decide deliberately: either accept that and get EU legal advice, or have clients fetch the official upstream onedir zip directly (GPG-verify the SHA2-256SUMS.sig) and live with the ad-hoc signature.
